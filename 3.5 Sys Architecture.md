# 3.5 System Architecture

## 3.5.1 Block Diagram

The system is a **Flask-SocketIO web application** that supports **dual-camera analysis** (ENTRY and EXIT). Each camera source — either an uploaded video file or a live RTSP/HTTP stream — is processed independently in a background daemon thread. Frames are resized to 672×448 and submitted to a **shared Batch Inference Engine** powered by **Ultralytics YOLO** (exported as a TensorRT `.engine` for GPU-accelerated inference). The engine collects frames from both camera threads into a batch (up to 40 frames, with a 15 ms wait window) and runs a single `predict()` call, returning `supervision.Detections` to each caller.

Each camera thread then feeds the detections into **ByteTrack** for multi-object tracking, which assigns persistent IDs so the same vehicle is not counted twice. The tracked centroids are tested against a **user-drawn counting line** using signed-distance geometry; when a centroid's signed distance flips sign (indicating it crossed the line) and the object is close enough to the segment, a crossing event is recorded. The ENTRY camera produces **IN** events and the EXIT camera produces **OUT** events.

Every crossing event creates a `VehicleEvent` carrying the vehicle class (Sedan, SUV, Pickup, Van, Motorcycle, Bus, Truck), direction (IN/OUT), timestamp, and min–max people-flow estimates derived from a configurable seat-capacity table. These events accumulate in an in-memory `SessionData` object and are delivered to the browser in real time via **Socket.IO** (vehicle events, statistics updates, progress). Annotated video frames are also pushed into per-camera **frame queues** and served to the browser as **MJPEG streams**.

For persistence, session data is written to **Firebase Realtime Database** in batched intervals (events every 30 s, statistics every 45 s) to minimise write costs, with a final complete save when processing ends. A combined statistics merge aggregates ENTRY and EXIT camera data to compute net vehicles and estimated people on site. Historical data is served through REST API endpoints and rendered as charts on the dashboard.

### Processing Pipeline Summary

| Step | Component | Detail |
|------|-----------|--------|
| 1 | **Input** | Upload video file (`POST /setup/upload-video`) or connect live stream (`POST /setup/configure-stream`) — one per camera role (ENTRY, EXIT) |
| 2 | **Line Setup** | First frame extracted and displayed; user draws a two-point counting line per camera (`POST /setup/save-line`) |
| 3 | **Start** | `POST /setup/start-processing` spawns a daemon thread per camera job |
| 4 | **Resize** | Each frame resized to 672×448 (Config.FRAME_WIDTH × FRAME_HEIGHT) |
| 5 | **Detection** | Frame submitted to shared `BatchInferenceEngine` → YOLO `predict()` on GPU → `sv.Detections` returned |
| 6 | **Tracking** | `sv.ByteTrack` assigns persistent tracker IDs across frames |
| 7 | **Counting** | Centroid signed distance to counting line; sign flip = crossing → `VehicleEvent` created |
| 8 | **People Flow** | `VEHICLE_CAPACITY` table maps vehicle type to min–max seat range (e.g., Bus: 1–50, Sedan: 1–5) |
| 9 | **Output** | Annotated video (file mode), MJPEG stream (live display), Socket.IO events (real-time stats), Firebase (persistence) |
| 10 | **Stop** | `POST /setup/stop-processing` sets `should_stop` flag; thread exits gracefully with final Firebase save |

## 3.5.3 Key Technical Components

### Detection Model
- **Ultralytics YOLO** (custom-trained) exported as a TensorRT `.engine` file for GPU-accelerated inference.
- 7 vehicle classes: Bus, Motorcycle, Pickup, Sedan, SUV, Truck, Van.
- Confidence threshold: 0.5.

### Batch Inference Engine
- Thread-safe singleton that owns the single YOLO model instance.
- Camera threads call `submit(frame)`, which enqueues the frame and blocks until the batch is processed.
- Batches up to 40 frames with a 15 ms collection window before firing.
- Uses the lowest confidence threshold in the batch so no detections are lost.

### Tracker
- **ByteTrack** (`supervision.ByteTrack`) with per-camera instances.
- Parameters: `track_activation_threshold=0.25`, `lost_track_buffer=30`, `match_thresh=0.8`.

### Line Crossing Detection
- Signed perpendicular distance from detection centroid to the two-point counting line.
- A crossing is registered when the signed distance changes sign between consecutive frames, the centroid is within 25 px of the line, and the projection falls within the line segment (with 10% margin).
- Each tracker ID is counted at most once (`counted_ids` set).

### People-Flow Estimation
- Each vehicle class maps to a min–max seat capacity (e.g., Sedan: 1–5, Bus: 1–50).
- ENTRY camera events are tagged **IN**; EXIT camera events are tagged **OUT**.
- Combined statistics merge ENTRY and EXIT data: `people_on_site = people_in - people_out` (min and max bounds).

### Persistence
- **Firebase Realtime Database** stores session data under `sessions/{session_id}`.
- Per-camera statistics (`statistics_ENTRY`, `statistics_EXIT`) plus merged `statistics`.
- Events stored as `events_ENTRY` / `events_EXIT` arrays.
- Writes are batched: events every 30 s, statistics every 45 s, with a final complete save on job completion.

### Real-Time Delivery
- **Socket.IO** (threading async mode): events emitted to session rooms for `vehicle_event`, `statistics_update`, `processing_progress`, `processing_complete`, `processing_error`.
- **MJPEG**: annotated frames pushed to per-camera `queue.Queue(maxsize=10)` and served via `GET /video-feed/<ENTRY|EXIT>`.

### Deployment
- **Docker** on `nvcr.io/nvidia/tensorrt` base image.
- **gunicorn + eventlet** WSGI server on port 7860.
- Firebase credentials via environment variable (`FIREBASE_CREDENTIALS_JSON` for cloud, file path for local).
- Compatible with **Hugging Face Spaces** deployment.
